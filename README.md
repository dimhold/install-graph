# A seventh of node_modules is the same package, twice

Five real projects, measured **on disk** rather than in a lock file or a
dependency graph. That distinction is the whole point: a graph resolved from
registry manifests counts distinct names, and cannot see what is physically
lying in the directory.

Nothing here is generated by a model. The whole measurement is three scripts,
one walk of `node_modules` and one pass over the npm registry.

## The number a graph cannot show you

In a working Angular front end, **532 of the 1,729 installed packages are second
and third copies of a name already present**. They take 52.2 MB and 7,904 files
— **14.4% of everything in `node_modules`.**

And 313 of those 532 are not version conflicts at all. **They are the same name
at the same version, laid out twice**, byte for byte. Across the three front
ends measured here the duplicate share runs 14.0% to 17.2%, and roughly 60% of
the duplicates are same-version copies.

| project | installed | duplicate copies | duplicate MB | share of disk | same version |
|---|---|---|---|---|---|
| frontend-a | 1 729 | 532 | 52.2 | **14.4%** | 313 |
| frontend-b | 1 542 | 487 | 102.5 | 14.0% | 312 |
| frontend-c | 1 709 | 528 | 60.6 | **17.2%** | 332 |
| fault-mcp | 141 | 2 | 0 | 0% | 1 |
| social-media | 6 | 0 | 0 | 0% | 0 |

Duplicate bytes are attributed to every copy after the largest one, so the
figure is the conservative reading of "extra".

## The number that put us here

The same front end lists **70** direct dependencies and has **1,729** packages on
disk, 363 MB and 50,649 files, at a tree depth of 12. Behind them stand **613
publishing accounts**; half the names have exactly one maintainer and 56.6% have
not published anything in over a year.

That ratio — 24.7 packages per line typed — is a known quantity and is not this
repository's contribution. See Prior work below, and note that published
dependency-amplification figures count distinct names in a resolved graph, which
is a different unit from copies on disk.

## What is *not* claimed

Project size does not predict the ratio. A 6-dependency MCP server in this
sample pulls 141 packages — a ratio of 23.5, indistinguishable from the big
front end. A 3-dependency TypeScript CLI pulls 6, a ratio of 2. **The ratio
tracks which dependencies you pick, not how large the project is**, and the
sample is far too small to say more than that.

The disproof condition was written before counting: if the ratio had come out
around 3–5 and been the same for large and small projects, there would have been
nothing to publish. See `CRITERIA.md`, committed before the first number.

## How it was measured

- `scan.mjs` — walks `node_modules` on disk. Counts every installed package,
  including nested duplicates, because three copies of one library at three
  versions are three copies of foreign code on disk. The de-duplicated count is
  reported separately. Size and file counts come from the tree; depth comes from
  `npm ls --all --json`, and a project whose tree is inconsistent is recorded as
  degraded rather than dropped — old projects are inconsistent, that is the
  field, not an error.
- `maintainers.mjs` — one registry request per distinct package name. The
  abbreviated packument (`application/vnd.npm.install-v1+json`) is cheaper but
  returns **neither `maintainers` nor `time`**; the first run came back with
  1,598 of 1,598 rows reading `maintainers: 0` before that was caught. Full
  packuments it is.
- `analyze.mjs` — joins the two, writes `results.json`.

Definitions, counting rules and the pre-registered disproof condition are in
`CRITERIA.md`. It was committed before any data existed, and it is not rewritten
after the fact: corrections are appended with a date.

## Run it

```bash
node scan.mjs --out out          # disk walk, no network
node maintainers.mjs --out out   # one request per distinct name, resumable
node analyze.mjs --out out       # join, results.json, table
```

`maintainers.ndjson` is append-only and doubles as resume state: interrupt it and
run it again.

## Caveats

Installed does not mean executed. `node_modules` carries tests, docs and build
artefacts of other people's packages; that is part of what arrives, and not an
answer to what runs. Separating live code from dead code is a different
measurement.

This is not a vulnerability count. `npm audit` counts against its own database
with its own method.

Five projects is a sample of five. The ratios here are observations, not base
rates for the ecosystem.

## Prior work, and what is actually new here

Written **after** the measurement, on 2026-08-27, which is the wrong order and is
recorded as such.

The framing this README opens with — packages per direct dependency — **is
published**. [*How Deep Does Your Dependency Tree Go? An Empirical Study of
Dependency Amplification Across 10 Package Ecosystems*](https://arxiv.org/pdf/2512.14739)
defines exactly that quantity as an amplification factor and reports it across
ten ecosystems, with npm averaging 30.9 direct and 52.8 transitive dependencies.
[Nakazawa's *Dependency Managers Don't Manage Your Dependencies*](https://cpojer.net/posts/dependency-managers-dont-manage-your-dependencies)
makes the qualitative case, and [*A comprehensive study of bloated dependencies
in the Maven ecosystem*](https://link.springer.com/article/10.1007/s10664-020-09914-8)
finds 82.5% of transitive dependencies bloated.

**Their 52.8 and this repository's 1,729 are not the same quantity, and the
difference is the point.** Published work resolves the dependency graph from
registry manifests and counts distinct names. This walks the installed
`node_modules` and counts **physical copies on disk**, duplicate versions
included. That is why a ratio of ~1.7 in their numbers and 24.7 here are not in
conflict: they are different units.

So what is left that the published work does not cover:

- **532 of the 1,729 packages on one project's disk are second and third copies
  of a name already installed** — 165 distinct names present at more than one
  version at once. A graph counted by name cannot see that at all.
- **Bytes and files on disk**: 363 MB and 50,649 files behind 70 lines of
  `package.json`.
- **Publishing accounts per project**: 613 distinct accounts behind one front
  end, 50.2% of names with a single maintainer, 56.6% with no publish in over a
  year — measured per real project rather than registry-wide.

The general rule this follows, learned the same week on a full npm census:
**dependency metadata is thoroughly occupied, what is physically on disk is
not.**
